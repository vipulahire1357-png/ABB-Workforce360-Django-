# Django migration feature map

Audit baseline: the repository is a FastAPI + SQLAlchemy + SQLite backend with a React/TypeScript/Vite single-page frontend. The existing `data/wir.sqlite3` database is accompanied by WAL files, and `data/uploads/workers` and `data/uploads/visitors` contain photographs. The working tree initially had user edits in `.env.example`, `README.md`, `backend/config.py`, `backend/dev_server.py`, and `frontend/vite.config.ts`; these are retained on branch `codex/django-migration-local`.

## Audited business-rule details

- Worker and visitor IDs are generated by existing HMAC-based services; worker numbers are allocated through `sequences`.
- Worker/visitor Aadhaar values are encrypted at rest and serializers expose only the last four digits.
- Gate transactions preserve accepted and rejected attempts. Entry is followed by exit; a second scan before 10 minutes is rejected, and one completed pair per person per local day is allowed by the current service.
- Canteen eligibility and visitor validity are enforced by server-side service code, not only UI state.
- CR80 card PDFs are two pages at 54 × 86 mm with barcode generation and the ABB logo.
- Existing automated tests cover schema compatibility, worker registration/authentication, card output, gate/canteen workflows, visitor expiry, and role restrictions.

## Verification notes

- `python manage.py check` passes; all 9 Django adapter tests pass; all 20 pytest tests pass.
- The primary SQLite database and worker/visitor photo directories were inventoried before and after startup; Django used the configured existing SQLite file.
- The deleted portable copy held one separate administrator row. It was not transferred because its credentials and relationship to the primary accounts were not established; recreate it with `python -m backend.create_admin` if it was needed.
- Manual operator login and full browser review remain for the user. The Django server is running locally for that review.
